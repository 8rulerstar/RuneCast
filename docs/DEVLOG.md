- 리샘플 32 → 64 (정확도 변화 거의 없음, 오히려 일부 악화)

## 1. 게임 컨셉 요약

**장르:** 자동전투(오토배틀러) + 실시간 제스처 캐스팅 액션
**플랫폼:** PC 우선 (마우스), 추후 모바일 export 고려
**엔진:** Unity (2D)
**개발 규모:** 잼/프로토타입 (짧은 스코프)

**핵심 루프:**
1. 용사들이 자동으로 진격·전투 (플레이어 개입 없이도 시스템은 계속 진행)
2. 용사 체력이 임계값 이하로 떨어지거나 강적 등장 시 "위기 신호" 발생
3. 플레이어가 마우스로 궤적을 그려 룬 시전 (마나 소모)
4. 궤적 판정 결과(정확도)에 따라 효과 강도 결정
5. 마나가 없으면 개입 불가 → 자동전투 결과에 그대로 맡겨야 함

**핵심 밸런스 원칙:** 용사들은 스스로는 이길 수 없게 설계 (약간 부족한 스탯). 플레이어의 룬 개입이 승패를 가르는 필수 변수여야 함.

**시전 중 시간:** 드래그하는 동안 `timeScale 0.2` (강한 슬로우). 완전 정지는 긴박감이 끊기고 무제한 고민을 허용해 난이도가 무너짐. 실시간은 손 느린 플레이어에게 가혹. → 슬로우가 중간값.

**룬 판정 방식 — 템플릿 단일 방식 (2026-07-31 개정):**

$P / $Q Point-Cloud Recognizer 하나로 통일. **룰 기반 분기는 폐기.**

1. 궤적을 N=64개 점으로 리샘플링
2. 크기·위치 정규화 (회전 정규화는 룬별 on/off — 화살은 방향이 의미이므로 off)
3. 등록된 모든 템플릿과 점-대-점 최소 매칭 거리 계산
4. 최근접 템플릿 = 판정, 거리 → 정확도 score(0~1)

*왜 룰 기반을 버렸나:* 원안의 `가로선=쉴드` / `화살표=발사체`는 둘 다 직선성이 높아 화살촉 감지 하나에만 의존하게 됨. 급하게 그으면 화살촉이 생략되는데, 급한 상황이 곧 이 게임의 사용 맥락이라 **가장 급할 때 가장 많이 틀리는** 판정이 됨. 점군 비교는 화살촉 유무가 거리에 자연히 반영되므로 이 문제가 사라짐.

*왜 딥러닝이 아닌가:* DL 분류기는 클래스당 수백 샘플이 필요하고 그걸 개발자가 직접 그려야 함. $P는 템플릿 1장으로 오각별·나선·멀티스트로크 마법진까지 커버. 복잡한 도형 인식이 목표라면 DL이 아니라 점군 매칭이 정답.
**DL은 폐기가 아니라 보류** — 이 구조로 굴리는 동안 템플릿과 플레이 로그가 쌓이고, 그게 나중에 ONNX 추론을 얹을 때의 학습 데이터가 됨. 지금 DL로 시작하면 데이터가 없어 아무것도 못 함.

*부수 효과:* 기본 룬과 커스텀 룬이 같은 메커니즘 → **구 Phase 5(커스텀 룬 등록)가 등록 UI만 붙이면 완성됨.** 도형 선택도 코드가 아닌 데이터 문제가 되어, 마음에 안 들면 GestureLab에서 다시 그려 교체하면 끝.

**룬 7종** (템플릿이므로 언제든 교체 가능). 회전 정규화는 쓰지 않고, 필요한 도형은 회전 변형을 여러 개 등록한다 — 지표각 정규화가 대칭성 약한 도형에서 불안정하기 때문.

| 룬 | 도형 | 마나 | 효과 |
|---|---|---|---|
| 화살 | 꺾쇠 `＞` | 15 | 꼭짓점 방향으로 발사체 (등급만큼 발수 증가) |
| 소용돌이 | 나선 `◎` | 22 | 끌어당김 + 둔화, **피해 없음** |
| 힐 | 원 `○` | 25 | 범위 회복 |
| 연쇄 번개 | 지그재그 `Ｚ` | 28 | 적 사이를 튕겨가며 감쇠 |
| 쉴드 | 삼각형 `△` | 30 | 삼각형 안 아군에게 보호막 |
| 별똥별 | 별 `☆` | 45 | 예고 후 광역 |
| ~~가르기~~ | ~~직선 `／`~~ | ~~12~~ | **비활성** — 아래 참조 |

**가르기를 뺀 이유:** 제일 싸고, 제일 빨리 그려지고, 그은 선 위의 적을 전부 벴다.
게다가 도형이 단순해서 등급까지 잘 나와 이중으로 유리했다 — 다른 룬을 쓸 이유가 없어졌다.
`RuneTemplateLibrary`의 직선 템플릿 블록만 주석 처리했고 `SlashWave.cs`는 그대로 있다.
**다시 켤 때 비용만 올리는 건 답이 아니다** — "그리기 쉬움 = 강함"이 구조적 문제라
사거리나 대상 수에 상한을 둬야 한다.
(뺀 뒤 실측: 나머지 인식률 그대로, 직선을 그으면 100% 거부되어 오발 없음)

**쉴드의 판정과 표시는 둘 다 삼각형이다.** 예전엔 바운딩 상자로 판정하고 상자를 그렸는데,
삼각형을 그렸는데 네모가 뜨고 유닛에는 동그란 링이 붙으니 무엇이 발동했는지 연결이 끊겼다.
그린 도형과 결과가 같은 모양이어야 한다.

**쉴드가 네모가 아닌 이유:** 네모는 점 대부분이 변 위에 있어 원(힐)과 가깝고, 다른 곳은 모서리 4곳뿐이다. 조금만 둥글게 그리면 원이 이겨서 **쉴드를 그렸는데 힐이 나갔다**. 실측으로 보통 정도 흔든 입력에서 네모 53% vs 삼각형 99.5%. 둥근 모서리 변형까지 넣어봤지만 84%가 한계였다.

**소용돌이에 피해가 없는 이유:** 나머지가 전부 피해/회복이라 선택지가 사실상 강도 차이뿐이었다. 적을 모아 별똥별을 떨구는 조합이 생겨야 룬이 늘어난 값을 한다.

### 정확도 → 위력·연출 (등급 시스템)

`score` → 4등급 **GOOD / GREAT / EXCELLENT / PERFECT**. 위력 배율은 smoothstep으로 `minPower 0.45` ~ `maxPower 1.7`.

**최하위 등급도 긍정어다.** 예전엔 "조잡"이었는데, 룬이 발동은 한 상황에서 플레이어를
깎아내릴 이유가 없다. 인식에 실패하면 어차피 "인식 실패"가 따로 뜨므로,
등급이 뜬 시점에서는 전부 성공이고 잘한 정도만 다르다.

**등급을 배율과 별도로 두는 이유:** 배율 1.31배와 1.34배는 화면에서 구분되지 않는다.
연출에는 **단위**가 필요하고, 플레이어가 "내가 잘 그렸다"를 알 수단은 사실상 연출뿐이다.
숫자만 커지면 아무 일도 일어나지 않은 것처럼 느껴진다.

등급이 올라가면 함께 커지는 것:
- 링·테두리 겹수, 파편·섬광 개수, 번개 굵기, 화살 발수, 연쇄 횟수, 소용돌이 흡인력
- 화면 흔들림(훌륭 이상), 효과음 음량, 등급색(HUD와 이펙트가 **같은 색**을 써서 인과를 잇는다)

실측 등급 분포:

| 손그림 변형 | GOOD | GREAT | EXCELLENT | PERFECT | 평균 배율 |
|---|---|---|---|---|---|
| 아주 깔끔 0.02 | 2% | 6% | 20% | 73% | 1.61 |
| 깔끔 0.04 | 3% | 11% | 36% | 50% | 1.54 |
| 보통 0.07 | 16% | 43% | 32% | 9% | 1.23 |
| 대충 0.10 | 52% | 39% | 8% | 1% | 0.89 |
| 막 그림 0.14 | 82% | 15% | 2% | 0% | 0.68 |

정성껏 그렸을 때와 막 그렸을 때 위력이 약 2.4배 차이 난다.

#### 도형 고르기 — 효과가 아니라 점군 거리로 정했다

후보 7개를 전부 넣고 합성 손그림으로 실측한 뒤 골랐다. 기준선은 6종 96.5%(보통 흔들림).

| 후보 | 전체 | 자기 인식률 | 결과 |
|---|---|---|---|
| 무한대 ∞ | 96.2% | 98.5% | 채택 |
| 하트 ♡ | 96.3% | 99.2% | 채택 |
| 깃발 ᛝ | 96.6% | 99.0% | 채택 |
| 아치 ⌒ | 94.3% | 90.8% | 탈락 — 꺾쇠(화살)와 서로 6~8% 오염 |
| 물결 ∿ | 95.7% | 87.2% | 탈락 — 나선(소용돌이)으로 5% 샘 |
| 나비 ⋈ | 92.5% | **73.0%** | 탈락 — 23%가 인식 실패 |
| 뾰족한 하트 | 95.6% | 87.0% | 탈락 — 삼각형(보호막)과 거리 0.129 → **0.077** 붕괴 |

**탈락한 것들의 공통점: 기존 도형을 부드럽게 하거나 뒤집은 것이었다.**
아치는 둥글린 꺾쇠고, 물결은 둥글린 지그재그고, 뾰족한 하트는 원에 삼각형을 섞은 것이다.
새 룬은 기존 것의 변형이 아니라 **없던 특징**을 가져와야 한다 —
∞는 덩어리가 둘이고, 깃발은 닫힌 고리에 꼬리가 붙어 있고, 하트는 홈과 꼭짓점이 같이 있다.

#### 회전 변형 ≠ 손떨림 여유 (이번에 새로 안 것)

깃발에 90°씩 4방향을 넣었더니 **낙서 오발동이 8.4%p 늘었다**. 고리+꼬리는 손이 아무렇게나
지나간 궤적과 제일 닮은 모양이라, 방향을 늘리면 그물만 넓어졌다. 깃대를 눕혀 그리는 사람은
없으므로 세운 것만 남겼다 — 인식률 100% 그대로, 오발동 13.9% → 8.2%.

반대로 고양은 방향을 4개 두고도 조금 기울여 그린 입력의 **15%가 통째로 인식 실패**했다.
회전 변형은 *자세*를 늘릴 뿐 *손떨림 여유*를 만들지 못한다. ±20° 기울기 변형으로 바꾸니 100%.

정리하면 **자세는 실제로 그리는 방향만, 여유는 기울기 변형으로.** 예전엔 둘을 같은 걸로 봤다.

#### 최종 실측 (템플릿 37개)

| 흔들림 | 전체 | 비고 |
|---|---|---|
| 또박또박 | 99.6% | |
| 보통 | 95.8% | 6종 기준선 96.5% 대비 −0.7%p |
| 급하게 | 70.1% | 대부분 인식 실패로 빠진다(오발동 아님) |

- 낙서 오발동 3.5% → **7.7%** (룬이 늘면 불가피하다. 단 99%가 최하 위력으로 나간다)
- 인식 비용 0.77 ms/획
- **가장 빡빡한 쌍: 소용돌이↔소생 0.120 / 힐↔소생 0.125 / 보호막↔소생 0.129**
  — 전부 거부 임계값 0.130 아래다. 소생이 9종 중 여유가 제일 적다.
  실측 인식률은 96.5%로 멀쩡하지만, **다음에 룬을 추가할 때 닫힌 곡선은 피해야 한다.**

#### 설계상 조심한 것

- **고양의 배율은 1을 기준으로 증가분에만 점수를 건다.** `1.55 × 0.45`로 곱하면
  못 그렸을 때 0.7배가 되어 강화 룬이 아군을 약하게 만든다.
- **소생은 시체가 없으면 마나를 쓰지 않는다.** 화면에 시체가 안 보이는데 55를 잃으면
  룬이 고장 난 줄 안다. 그래서 좌표 환산을 마나 소모보다 먼저 한다.
- **소생은 시체가 사라지기 전(1.1초)에만 걸린다.** 언제든 되살릴 수 있으면
  지키는 룬이 통째로 무의미해진다. 회복량이 아니라 반응 속도를 요구한다.
- **봉화는 획의 시작점(깃대 밑)에 깔린다.** 바운딩박스 중심을 쓰면 고리 쪽으로 치우쳐서
  손으로 찍은 자리와 불이 어긋난다.
- 전용 효과음이 없어서 가장 가까운 클립을 피치를 크게 벌려 쓴다
  (고양 ×1.35 / 소생 ×0.78 / 봉화 ×1.15). 같은 소리를 같은 높이로 두 룬에 쓰면
  그때부터 피드백이 아니라 소음이 된다.

#### 최적화

- **`Loadout.Sum`이 장착 슬롯마다 전체 문양 목록을 선형 탐색**하고 있었다.
  HUD가 룬 9종의 마나 비용을 프레임당 36번 묻는데(OnGUI ×2 × 룬 9 × 2회),
  10연차를 몇 번 돌려 문양이 300개면 **가만히 있어도 프레임마다 수만 번 순회**했다.
  → `[효과, 룬]` 표로 미리 접고 장착이 바뀔 때만 다시 만든다. O(장착×문양) → O(1).
- **OnGUI를 Repaint에서만 그린다.** HUD와 떠오르는 숫자는 버튼이 없고 라벨뿐이라
  Layout 패스에서 도는 계산이 전부 낭비였다. 그대로 절반.
- **`TraceRenderer`가 점 하나 늘 때마다 전체를 다시 썼다.**
  잉크가 커진 후반엔 한 획이 270점이라 획 하나에 SetPosition이 270×270×2번.
  → 꼬리만 채운다.
- 마나 비용 문자열, 화살 판정 버퍼 등 매 프레임 생기던 쓰레기 제거.

> 캐시 버전을 `Rebuild`가 아니라 `Invalidate`에서 올린 이유:
> Rebuild에서 올리면 UI가 "버전이 그대로니 다시 계산할 필요 없다"고 판단해
> Rebuild를 부르지 않고, 그래서 버전도 안 오르는 순환에 빠진다. 낡은 값이 영영 남는다.

#### 연출 — 그은 선이 인식된 도형으로 정돈된다

이 게임에서 플레이어가 가장 오래 쳐다보는 물건은 자기가 그은 선이다.
그런데 판정이 끝나면 그 선은 그냥 흐려질 뿐이고, **무엇으로 인식됐는지**는
화면 가운데 글자로만 전달됐다 — 손끝을 보던 시선에서 먼 자리다.

시전에 성공하면 그은 선이 0.22초에 걸쳐 인식된 템플릿 모양으로 정돈되고,
그동안 등급색으로 물든다. "내 낙서가 룬이 되었다"가 그 자리에서 읽히고,
**다음에 어떻게 그려야 더 잘 나오는지도 같이 가르친다** — 등급 글자보다 구체적이다.

만들면서 실측으로 잡은 것 둘:

- **점 개수는 그은 선 쪽에 맞춘다.** 반대로 템플릿(32점)에 맞추면 시전하는 순간
  선이 성기게 바뀌면서 툭 각져 보이고, 나선은 정돈된 결과가 원본보다 조잡해진다.
- **닫힌 도형은 시작점을 맞춰야 한다.** 원을 아래에서부터 그린 사람의 선은
  진행도만 맞추면 정돈될 때 고리를 한 바퀴 돌아버린다. 템플릿을 여러 시작 위치로
  돌려보고 제일 덜 움직이는 것을 고른다.

  실측(점 이동량 / 도형 크기): 보정 없음 **50~82%** → 보정 있음 **1.2~1.9%**.
  즉 보정이 없으면 점이 도형 크기만큼 움직인다 — 화면에서는 그냥 오작동으로 보인다.

그 밖에 마나가 모자라 튕기면 마나 게이지가 붉게 떨고, 잉크가 잘리면 잉크 게이지가 떤다.
실패 사유가 화면 가운데 글자로만 있으면 그리던 시선에서 안 읽힌다.

### Phase 4-d — 메타 화면 재구성 (2026-08-01)

모바일 성장형 게임(탕탕특공대류)의 관습을 참고했다. **그림을 베낀 게 아니라
화면 구성 규칙을 가져왔다** — 에셋은 그대로 Crusenho 팩이다.

#### 가져온 것

| | 왜 |
|---|---|
| **주력(전투력) 단일 수치** | 성장이 룬 레벨 9개 + 문양 5칸 + 잉크 단계로 흩어져 있어서, **강화를 눌러도 화면에서 달라지는 게 없었다.** 모든 투자가 같은 숫자로 모여 오르는 걸 보여준다 |
| **빨간 점(레드닷)** | 파편이 강화에 충분한지 알려면 대장장이에 들어가 목록을 훑어야 했다. 그래서 대부분 안 확인하고 **파편이 그냥 쌓였다** |
| **상단 고정 재화 바** | 재화가 화면마다 다른 자리에 있으면 볼 때마다 눈이 헤맨다 |
| **큰 "다음 도전" 버튼** | 격자만 있으면 어디부터 할지 매번 찾아야 한다. 켜자마자 누를 것이 화면에서 제일 큰 물건이어야 한다 |
| **하단 내비게이션** | 우상단에 흩어 두면 화면마다 자리가 달라지고, 폰에서 손가락이 제일 안 닿는 자리다 |

#### 일부러 안 가져온 것

- **세로 화면 배치.** 그쪽은 세로에 조이스틱이고 이 게임은 가로에 그리기다.
  화면 가운데를 비워 둬야 한다 — **거기에 그림을 그리는 게 이 게임**이라
  세로용 하단 시트나 가운데 쇼케이지를 옮기면 정작 핵심 조작을 가린다.
- **캐릭터 쇼케이스.** 조작하는 캐릭터가 없다. 있지도 않은 것을 위한 자리를 만들 수 없다.
- **일일 보상·출석 같은 재방문 장치.** 시스템은 쉽지만 **매일 켤 이유가 되는 콘텐츠가
  아직 없다.** 스테이지 12개짜리 게임에 출석부터 붙이면 빈 껍데기가 된다.

#### 주력 계산

```
주력 = 100 + Σ(룬 레벨-1)×20 + Σ(장착 문양 등급가중치×값) + 잉크단계×60 + 별×4
```

**정확한 강함을 재는 게 목적이 아니다.** 전투에는 전혀 쓰이지 않는다(실제 위력은
`Loadout`이 따로 계산한다). 이 값을 전투에 먹이면 표시용이 아니라 밸런스 축이
하나 더 생겨서, 손댈 때마다 밸런스가 같이 움직인다.

중요한 건 **어떤 투자를 해도 반드시 오른다**는 것 하나다.

#### 만들면서 잡은 것

- CTA 라벨이 상단 재화 바를 침범하고 있었다(바가 T+52까지인데 라벨이 T+42).
  미리보기를 렌더링해서 찾았다 — `store/preview_home.py`가 MetaUI와 같은 좌표로
  화면을 그린다. **여기서 겹치면 게임에서도 겹친다.**
- 스테이지 목록을 위에 붙여 두면 화면 아래 절반이 통째로 비었다. 남은 공간
  가운데로 옮겼다.

### Phase 4-e — 타이틀 (2026-08-01)

타이틀이 글씨와 버튼뿐이라 **이 게임이 뭔지 아무것도 안 보여줬다.**
정체는 캐릭터도 전투도 아니고 "손으로 도형을 그려서 마법을 건다"인데,
그건 정지 화면에 안 담긴다 — 움직여야 읽힌다.
(스토어 스크린샷이 핵심을 못 보여주는 것과 정확히 같은 문제다.)

**`UI/TitleRune.cs` — 룬이 저절로 그려진다.**

- 실제 템플릿을 실제 궤적 렌더러와 같은 방식(글로우 + 심)으로 그린다.
  따로 만든 로고 애니메이션이 아니라 **게임이 실제로 하는 일**이라,
  룬을 추가하면 타이틀에도 저절로 나온다.
- 그리기 1.1초 → 머무름 1.0초 → 사라짐 0.5초. 다 그린 순간 살짝 밝아진다(시전 감각).
- 끝으로 갈수록 느려지는 곡선. 사람이 도형을 마무리할 때의 속도에 가깝다.
- `Time.unscaledDeltaTime` — 일시정지 상태로 들어와도 멈추면 안 된다.

**배치는 화면비로 갈린다.** 가로로 길면 룬이 왼쪽 / 글씨가 오른쪽,
좁으면(4:3 등) 룬이 가운데 위 / 글씨가 아래. 좁은 화면에서 좌우로 나누면 둘 다 낀다.

크기는 화면 높이의 **0.33배**. 처음엔 0.42로 뒀는데 별(제일 큰 도형)이 화면 높이의
77%를 먹어서 글씨 쪽까지 밀고 들어왔다 — `store/preview_title.py`로 보고 줄였다.
주인공이되 화면을 삼키면 안 된다.

진행이 있으면 **주력 · 별 · 깬 판**을 버튼 위에 요약한다. 켜자마자 "내 계정"이라는
감각이 생기는 자리고, 주력은 그러라고 만든 숫자다. 할 일이 있으면 이어하기 버튼에
빨간 점도 붙는다 — 스테이지 선택까지 안 들어가도 보이게.

### Phase 4-f — 튜토리얼 · 체력바 (2026-08-01)

#### 체력바가 양쪽에서 줄고 있었다

스프라이트 기준점이 한가운데라 스케일만 줄이면 가운데를 기준으로 양쪽이 같이 좁아진다.
체력바는 **왼쪽 끝이 고정된 채 오른쪽만 닳아야** "얼마 남았나"가 길이로 읽힌다.
줄어든 만큼 왼쪽으로 밀어서 왼쪽 모서리를 붙들었다.

```
가득: 폭 W    중심  0        왼끝 -W/2
절반: 폭 W/2  중심 -W/4      왼끝 -W/2
바닥: 폭 0    중심 -W/2      왼끝 -W/2
```

#### 튜토리얼 — 막지 않고, 해보면 사라진다

**팝업으로 만들지 않았다.** 확인 버튼을 누르게 하면 사람은 글을 읽지 않고
**닫는 법부터 배운다.** 전투가 그대로 돌아가는 채로 화면 아래에 한 줄을 띄우고,
플레이어가 실제로 그 행동을 하면 저절로 사라진다.

| 단계 | 언제 | 끝나는 조건 |
|---|---|---|
| 그리기 | 첫 전투 진입 | **한 번 시전에 성공하면** |
| 등급 | 첫 시전 성공 | 5.5초 |
| 잉크 | 처음 획이 잘렸을 때 | 5.5초 |
| 마나 | 처음 마나가 모자랐을 때 | 5.5초 |
| 클리어 | 첫 클리어 | 5.5초 |

**실패 안내는 겪은 직후에만 뜬다.** 마나가 뭔지 미리 설명해 봐야 무슨 말인지 모른다.

첫 단계에서는 그릴 도형을 **직접 그려 보인다**. 글로 "꺾쇠를 그리세요"라고 쓰면
꺾쇠가 뭔지, 얼마나 크게, 어느 방향으로 그려야 하는지가 하나도 안 담긴다.
타이틀의 룬 애니메이션을 `UI/RuneTracer.cs`로 일반화해서 같은 것을 쓴다.

##### 만들면서 잡은 것

- **읽기만 하는 안내는 띄우는 즉시 기록하고, 그리기 안내는 실제로 그려야 기록한다.**
  처음엔 화면에서 걷을 때 무조건 기록했는데, 그러면 첫 판에서 한 번도 안 그려보고
  나간 사람은 안내를 영영 다시 못 본다.
- 시연 도형이 화면 가운데 뜨는데 문구는 "왼쪽 도형"이라고 했다. 미리보기를
  그려 보고 찾았다.

설정에 "튜토리얼 다시 보기"를 넣었다. 전체 초기화에도 포함된다.

### Phase 4-g — 메뉴와 전투 화면 분리 (2026-08-01)

메뉴가 전투 화면 **위에 반투명 막을 덮는** 방식이었다(0.62~0.78). 그래서 타이틀·
스테이지 선택·대장장이 뒤로 초원과 바위가 계속 어른거렸다 — 화면이 바뀐 게 아니라
뭔가 덮인 것처럼 보이고, 무엇보다 **읽어야 하는 글씨 뒤로 풀 무늬가 지나간다.**

**배경을 아예 둘로 나눴다.** 전투는 초원(`Backdrop`), 그 밖은 `MenuBackdrop`
(그라디언트 + 비네트 + 아주 느린 알갱이).

#### IMGUI로 덮는 방법은 못 썼다

OnGUI는 항상 씬 위에 그려진다. 메뉴 UI가 불투명하게 덮으면 **타이틀에서 룬을 그리는
`RuneTracer`까지 같이 가려진다.** 그래서 배경도 월드 오브젝트여야 했다.

#### 판정은 UI 상태가 아니라 "전투가 진행 중인가"로

```
초원 = BattleManager.Running || State == Result
```

상태로 판단하면 전투 중에 일시정지 → 설정을 열었을 때 상태가 `Settings`로 바뀌면서
**유닛은 그대로 서 있는데 바닥만 사라진다.** `Running`은 스테이지를 시작할 때 켜지고
나갈 때(`Abort`) 꺼지므로, 그 사이에 어떤 화면을 열든 배경이 유지된다.

**결과 화면도 전투로 친다.** 방금 싸운 전장이 뒤에 남아 있어야 그 판의 결과라는 게
읽히고, 유닛이 그대로 있는데 바닥만 바뀌면 허공에 뜬다.

| 화면 | Running | 배경 |
|---|---|---|
| 타이틀 · 스테이지 선택 · 대장장이 | false | 메뉴 |
| 메뉴에서 연 설정 · 크레딧 | false | 메뉴 |
| 전투 · 일시정지 · 전투 중 설정 | true | 초원 |
| 결과 | false | **초원** |

#### 막 두께

가릴 것이 없어졌으므로 타이틀 0.20 / 스테이지 선택 0.22로 낮췄다 —
남은 몫은 배경 알갱이와 글씨가 겹칠 때의 대비뿐이다.
대장장이 0.9 → 0.42, 크레딧 0.94 → 0.62.
**결과 화면만 0.78 그대로** — 거기는 뒤에 전장이 있어서 눌러 줘야 글씨가 읽힌다.

호출부에 숨은 배율을 두지 않았다. 한때 `alpha * 0.28`로 일괄 적용했는데,
그러면 다음에 값을 손댈 때 화면에서 보이는 것과 코드의 숫자가 어긋난다.

### Phase 4-h — 버그·미감·피드백 손질 (2026-08-01)

#### 같은 실수를 두 번 했다

`Loadout.Sum`이 장착 칸마다 전체 문양 목록을 선형 탐색하던 걸 고쳐 놓고,
**주력(`CombatPower`)과 알림(`Notify`)에서 똑같이 되살렸다.** 둘 다 상단 재화 바·
타이틀·대장장이 탭에서 매 프레임 읽는 값이라, 문양이 300개면 화면에 아무 변화가
없어도 프레임마다 수천 번을 순회한다.

이번엔 개별 캐시 대신 **저장 데이터에 번호를 붙였다** —
`PlayerData.Revision`, `StageProgress.Revision`. 값이 바뀔 때마다 오르고,
파생 값을 캐시하는 쪽은 번호만 보면 된다. 파생 값을 하나 더 만들 때
캐시를 빠뜨릴 여지를 줄이는 게 목적이다.

> 배치(10연차) 중에도 번호를 올린다. 파일에 쓰는 시점이 아니라
> **값이 바뀐 시점**이 캐시가 낡는 시점이다.

#### OnGUI는 한 프레임에 여러 번 돈다

주력이 차오르는 연출을 넣고 보니 `Time.unscaledDeltaTime`을 OnGUI에서 더하고 있었다.
버튼이 있는 화면은 Repaint만 걸러낼 수도 없어서(입력을 못 받는다) 시간이 프레임당
두세 번 더해지고, 숫자가 그만큼 빨리 차오른다. `Time.frameCount`로 한 프레임에
한 번만 돌게 막았다.

#### 피드백

- **주력이 차오른다** (`UI/PowerTicker.cs`). 1840 → 1860이 그냥 바뀌면 화면에서
  아무 일도 아니다 — 강화를 누른 사람은 파편이 줄어든 것만 느끼고 뭘 얻었는지는
  못 느낀다. 숫자가 차오르고, 오르는 동안 밝아지고, 오른 양이 `+20`으로 옆에 뜬다.
  상단 바와 타이틀 요약이 **같은 ticker를 공유한다** — 두 개를 두면 화면을 옮길 때마다
  각자 다른 값을 보여준다.
- **적을 쓰러뜨리면 터진다.** 소리와 사망 모션만 있었는데, 사망 모션은 몇 프레임에
  걸쳐 재생돼서 룬으로 여럿을 한 번에 정리했을 때 "쓸어버렸다"가 화면에 안 남았다.
  아군 쪽을 더 크고 붉게 — 잃은 것이 눈에 더 오래 남아야 한다.

#### 미감

- 전투 HUD의 룬 목록 뒤에 얇은 판을 깔았다. 초원 위에 맨 글씨를 올려서 밝은 풀
  타일과 겹치는 자리에서 글자가 사라졌다. 시전 중에 비용을 확인하는 목록이라
  안 보이는 순간이 있으면 안 된다. (판 폭은 2열 내용 오른쪽 끝을 덮도록 계산해서 잡았다)
- 빨간 점이 매 호출 `"ci" + size` 문자열을 만들고 있었다. 텍스처를 캐시했다.

### Phase 4-i — 효과음 · 최적화 · 연출 (2026-08-01)

#### 버튼에 소리가 아예 없었다

게임 전체의 버튼이 무음이었다. 눌렀는지 아닌지가 그림으로만 전달됐다.

`UiSkin.DrawButton` **한 곳에서** 낸다. 화면마다 붙이면 반드시 어딘가 빠지고,
그러면 "어떤 버튼은 소리가 나고 어떤 버튼은 안 나는" 게 된다 —
**그건 소리가 없는 것보다 나쁘다.**

못 누르는 버튼을 눌렀을 때도 소리를 낸다. 예전엔 아무 일도 안 일어나서
버튼이 고장 난 건지 조건이 안 맞는 건지 알 수 없었다.

> 거절음은 전투의 마나 부족음과 같은 파일이라 피치를 1.7로 멀리 띄웠다.
> 대장장이의 장착 실패도 같은 소리로 통일했다 — 한 화면에 "안 됨" 소리가 둘이면
> 규칙이 아니라 사고처럼 들린다.

#### 결과 화면의 별이 무음이었다

하나씩 늦게 뜨는 연출은 있었는데 소리가 없었다. **음을 하나씩 올린다** —
같은 음이 세 번 나면 몇 개가 떴는지 귀로 안 세어지고, 올라가면 세 번째가 절정이 된다.
방금 뜬 별만 살짝 커졌다 돌아오고, 3별이면 화면도 더 흔들린다.

> `_starsHeard`를 결과 화면에 들어올 때 되돌린다. 안 그러면 지난 판의 3이 남아
> **두 번째 클리어부터 소리가 안 난다.**

#### 웨이브 시작에 클리어 소리를 쓰면 안 된다

배너만 뜨고 소리가 없어서, 그리는 중이면 새 무리가 들어온 걸 놓쳤다.
처음엔 `WaveClear`를 썼다가 바꿨다 — 물결을 정리한 직후 2초 뒤에 다음 물결이
시작되므로 **같은 소리가 연달아 나고, 그러면 둘 다 아무 뜻이 없어진다.**
낮게 깐 착탄음이 "뭔가 다가온다"로 읽힌다. 마지막 물결은 더 낮게.

#### 최적화 — 매 프레임 만들던 문자열

OnGUI는 한 프레임에 두세 번 돈다. 값이 드물게 바뀌는데 매번 `string.Format`을
돌리면 그만큼 쓰레기가 쌓이고, 모바일에서는 GC가 끊김으로 나타난다.

| 무엇 | 얼마나 | 어떻게 |
|---|---|---|
| 스테이지 카드 12장의 제목·정보 | 프레임당 24~72개 | 언어 바뀔 때만 |
| 전투 HUD 마나 표시 | 프레임당 2~3개 | 정수가 바뀔 때만 |
| 전투 HUD 물결·생존 줄 | 프레임당 2~3개 | 값이 바뀔 때만 |
| 뽑기 연출의 고리 텍스처 키 | 연출 중 프레임당 1개 | 한 번만 |

> 캐시에 **언어도 같이 본다.** 값이 그대로인 채로 언어만 바뀌면 낡은 말이 남는다.

### Phase 4-j — 망령 · 밸런스 실측 (2026-08-01)

#### 개입으로만 잡을 수 있는 적 — 망령

**이 게임의 전제가 실제로는 작동하지 않고 있었다.** "자동전투는 샌드백이고 개입이
본체"라고 해놓고, 아군이 알아서 다 잡을 수 있으면 그리는 건 선택사항이다.

망령은 **선택을 없앤다** — 평타가 통하지 않고 룬 피해만 받는다.

세지 않게 잡았다(체력 90, 공격 6, 느림). 위협의 근거가 "강해서"가 아니라
**"아군이 손을 못 대서"**여야 한다. 세기까지 하면 그냥 어려운 적이다.
화살 한 번(≈95)이면 정리되므로 여러 번 쓸 필요는 없고, 마나가 조인 후반에
두세 마리가 섞이면 그것만으로 자원 문제가 된다.

구현은 5줄이었다 — `TakeDamage`가 이미 `fromRune`을 받고 있었기 때문이다
(피해 숫자를 크게 띄우려고 만든 것). 새 경로를 만들면 어느 효과가 룬인지
두 곳에서 관리하게 되고 반드시 어긋난다.

**아무 일도 안 일어나면 버그처럼 보인다.** 평타가 통과할 때 "무효"를 띄우고
막힌 소리를 낸다. 겉모습도 다르게 — 푸른 유령빛 + 도는 고리.
겉이 같으면 규칙을 때려 보기 전에는 알 수 없고, 그건 알려주는 게 아니라 숨기는 것이다.

#### 밸런스를 처음으로 실측했다

`tools/sim_battle.py`가 UnitAI의 규칙(0.2초 재조준 · 사거리 · 공격 주기)을 그대로
돌린다. 개입 없이 각 판이 어떻게 끝나는지 재고, 그 다음 "초당 몇 피해를 넣어줘야

- 1·3판은 **아군 전원이 살아남아 자동으로 3별** — 그리는 게 완전히 선택사항

- 2판이 3판보다 어려운 역전도 있었다

- 한국어/영어의 자리표시자 개수 불일치 (한국어는 멀쩡한데 영어로 바꾸면 깨지는 것)

### Phase 4-l — 최적화 · 오류 (2026-08-01)

#### 마나가 새고 있었다 — 2장 전체가 무너지는 구멍

`ManaPool`이 `Time.unscaledDeltaTime`으로 회복하고 있었다.
"슬로우 중에 오래 고민한다고 마나가 덜 차면 이중 처벌"이라는 이유였는데,
그 결정이 **두 개의 구멍**을 만들고 있었다.

1. **일시정지 중에도 찬다.** 멈추고 10초 기다렸다 풀면 마나가 90 늘어난다.
2. **드래그를 누른 채 가만히 있으면** 시간은 0.2배로 흐르는데 마나는 실시간으로 찬다.
   **잉크는 움직여야 닳으므로 아무 대가가 없다** — 게임 시간 대비 5배로 마나를 번다.

2장 전체가 "마나가 없으면 지켜볼 수밖에 없다"에 걸려 있는데 통째로 무너지는 구멍이었다.

`Time.deltaTime`으로 바꿨다. 원래 걱정했던 "고민하는 시간"은 사실 슬로우가 아니다 —
**슬로우는 그리는 동안만 걸린다.** 무엇을 그릴지 정하는 시간은 원래 속도로 흐르므로
이중 처벌이 아니었다. 적도 같이 느려지니 비율도 그대로다.

| 10초 동안 버는 마나 | 전 | 후 |
|---|---|---|
| 보통 플레이 | 90 | 90 |
| 계속 그리는 중(0.2배) | 90 | 18 |
| 일시정지 | 90 | **0** |

#### 대장장이 목록이 안 보이는 줄까지 그리고 있었다

`GUI.BeginScrollView`는 스크롤 밖을 **잘라내 줄 뿐 그리는 일 자체는 그대로 시킨다.**
10연차를 몇 번 돌리면 문양이 300개가 되는데, 그러면 300줄을 매번 그리고
줄마다 `GlyphTable.Describe`가 문자열을 만든다. OnGUI가 프레임당 두세 번 도니
**프레임마다 문자열 900개.** 화면에 실제로 보이는 건 8줄 남짓이다.

스크롤 위치로 보이는 범위만 그리게 했다.

#### 망령 고리가 몸보다 작았다

고리는 스폰 콜백에서 만들어지는데, 그 시점엔 `Awake`가 아직 안 돌아서 몸이 없다
(`SetActive(false)` 상태로 컴포넌트를 붙이기 때문이다). 그래서 몸 배율을 모른 채
고정값 1.25로 잡혀 있었고, 배율 2.0인 망령에서는 **고리가 몸 안에 들어가 있었다.**
`SetSpriteMode`가 배율을 아는 유일한 자리라 거기서 맞춘다.

#### 확인만 하고 넘어간 것

- **컴파일러 경고를 처음으로 켰다**(`-warn:4`). 3개 타깃 모두 0건.
- 문구 검사 0건, 폰트 빠진 글자 0.

#### 업적 — 잘 그릴 이유를 만든다

목표가 "스테이지 12개 클리어"뿐이면 잘 그릴 이유가 없다. 별은 아군을 지키면

8종. 보상은 파편과 스킨뿐 — **성능이 붙는 보상은 안 준다.**
그러면 업적이 "해도 되는 것"이 아니라 "해야 하는 것"이 된다.

세는 것(PERFECT 횟수·망령 처치·소생 인원)은 조건과 같은 파일에 뒀다.
판정과 집계가 떨어져 있으면 반드시 어긋난다.

**집계는 `RuneCaster` 한 곳에서만 알린다.** 각 효과 안에서 세면 룬을 추가할 때마다
빠뜨리고, 그러면 어떤 룬은 세어지고 어떤 룬은 안 세어진다.

업적과 스킨을 한 탭에 둔 이유: **업적이 스킨을 연다.** 따로 두면 왜 이 스킨이
잠겼는지 보려고 화면을 오가야 하고, 그러면 업적이 목표로 안 읽힌다.

큰 룬의 연출을 볼 때는 제한이 방해만 된다. 진단 패널과 같은 자리(설정 아래쪽)에
뒀다 — 개발용이라는 게 자리로 읽혀야 한다.

`sim_battle.py`는 "초당 몇 피해면 이기나"를 잰다. 그 표로 보면 8~12판이
**"도와도 힘듦"**이었다. 그런데 그 모델에는 시전 슬로우가 없었다.

```
화살 한 번   마나 15, 피해 94   → 마나당 6.2
지속 화력    초당 마나 9 ÷ 15 × 94 = 56 DPS

한 번 그리는 데 실제 0.7초가 걸리지만
시전 슬로우(0.2배) 때문에 게임 시간은 0.14초뿐이다
→ 그리는 동안 적은 사실상 멈춰 있다
```

**슬로우가 개입을 얼마나 세게 만드는지가 "초당 피해"라는 숫자에 안 담긴다.**

`sim_player.py`를 새로 만들었다 — 마나 회복·룬별 비용·그리는 시간·슬로우를
전부 규칙대로 돌린다. 정책은 "살 수 있는 것 중 마나당 피해가 큰 룬"으로 단순해서,
사람은 이보다 잘한다. **하한선을 재는 도구다.**

| 판 | 개입 없음 | 강화 1.0 | 강화 1.6 이상 |
|---|---|---|---|
| 1~6 | 1·3판만 승 | 전부 3별 | 전부 3별 |
| 7~9 | 전패 | 전부 3별 | 전부 3별 |
| 10~12 | 전패 | 승리 2별 | 3별 |

읽는 법:

- **개입하지 않으면 4판부터 전부 진다.** 이 게임이 하려던 것이 그것이다.
- 강화 없이도 12판까지 이긴다. 다만 마지막 세 판은 2별이라 3별을 채우려면
  대장장이로 돌아가야 한다 — **메타가 그때 필요해진다.**
- 앞의 아홉 판은 꾸준히 그리면 강화 없이 3별이 난다.
  12판짜리 게임의 앞구간으로는 무난하지만, **콘텐츠가 늘면 여기를 다시 조여야 한다.**

> 두 시뮬레이터가 서로 다른 답을 낸 게 이번의 교훈이다.
> 모델이 무엇을 빠뜨렸는지 모르면 그 숫자를 믿을 수 없다.

### Phase 4-p — 최적화 (2026-08-01)

#### 적을 하나 잡을 때마다 디스크에 쓰고 있었다

업적 집계를 넣으면서 세는 곳마다 곧장 파일을 쓰게 해뒀다.
`OnRuneKill`은 **룬으로 적을 하나 쓰러뜨릴 때마다** 불린다 —
별똥별로 12마리를 한 번에 정리하면 한 프레임에 디스크 쓰기가 12번이다.

| 한 판(적 60·룬 40회) | 전 | 후 |
|---|---|---|
| 파일 쓰기 | 100회 | 1회 |
| `Notify` 재계산 | 100회 | 0회 |

미뤄뒀다가 안전한 지점에서 한 번만 쓴다 — 스테이지 끝, 보상 수령,
그리고 **앱이 백그라운드로 갈 때**(모바일은 종료 없이 죽으므로 `OnApplicationQuit`만
믿으면 안 된다).

**달성과 수령은 즉시 쓴다.** 미루다 앱이 죽으면 보상이 사라지는데,
그건 세는 숫자 몇 개를 잃는 것과 무게가 다르다.

#### 갱신 번호를 용도별로 나눴다

저장 번호(`Revision`) 하나로 빨간 점과 진행 막대를 둘 다 판단하고 있었다.
그런데 둘은 **갱신 빈도가 백 배쯤 다르다** — 받을 보상은 업적을 달성해야 바뀌지만,
세는 숫자는 적을 잡을 때마다 바뀐다.

- `Revision` — 달성·수령·불러오기·초기화에만. 빨간 점(`Notify`)이 본다
- `CounterRevision` — 세는 숫자가 바뀔 때. 진행 막대가 본다

나누기 전에는 적을 하나 잡을 때마다 `Notify`가 문양 목록 전체를 다시 훑었다.

#### 남아 있던 매 프레임 문자열

| 어디 | 얼마나 |
|---|---|
| 전투 화면 스테이지 제목 (`1. 첫 교전`) | 프레임당 2~3개 |
| 기록 탭의 진행 문구·보상 버튼 | 프레임당 수십 개 |
| 각인 화면의 룬 버튼 9개 | 프레임당 20여 개 |
| 업적 알림의 보상 글자 | 떠 있는 동안 매 프레임 |

전부 값이 바뀔 때만 만들게 했다. **캐시는 언어도 같이 본다** —
값이 그대로인 채 언어만 바뀌면 낡은 말이 남는다.

### Phase 4-q — 화면별 음악 (2026-08-01)

배경은 메뉴/전투로 갈라 놨는데 **음악은 그대로였다.** 그러면 화면이 바뀐 게
귀로는 안 읽히고, 배경만 갈라 놓은 효과도 반쯤 죽는다.

| | 곡 |
|---|---|
| 타이틀 · 스테이지 선택 · 대장장이 | `bgm_menu`, `bgm_cloak1~3` |
| 전투 · 일시정지 · 결과 | `bgm_wave1~8` (판마다 무작위) |

판정은 배경과 **같은 기준**을 쓴다(`BattleManager.Running || State == Result`).
두 기준이 갈라지면 배경은 초원인데 음악은 메뉴인 상태가 생긴다.

#### 같은 무리 안에서는 안 갈아끼운다

스테이지 선택 → 대장장이 → 설정을 오갈 때마다 곡이 처음부터 다시 시작하면
**같은 도입부만 반복해서 듣게 된다.** 무리가 실제로 바뀔 때만 넘어간다.

#### 전투는 판마다 다른 곡

같은 판을 여러 번 다시 할 때 매번 같은 곡이면 재도전이 더 지겹게 느껴진다.
직전 곡과 같으면 다음 곡으로 밀어낸다.

#### 0.45초 크로스페이드

툭 끊고 바꾸면 화면 전환보다 소리가 먼저 튄다. 앞 절반은 줄이고 뒤 절반은 키운다.
설정의 음량 조절이 **페이드 중에는 볼륨을 안 건드린다** — 안 그러면 넘어가는 도중에
소리가 튄다.

### 잉크 — 한 획에 그을 수 있는 길이 (메타 성장)

마나가 **얼마나 자주** 쓰느냐를 제한한다면, 잉크는 **얼마나 크게** 쓰느냐를 제한한다.
축이 겹치지 않아 둘을 같이 둘 수 있다.

이 게임에 특히 잘 맞는 이유가 셋이다:

1. 효과 범위가 이미 "그린 크기"에서 나온다. 길이를 조이면 범위가 그대로 줄어든다.
2. **인식기가 크기를 정규화하므로 작게 그려도 인식률은 그대로다.**
   잉크 제한은 "못 알아듣게" 만드는 게 아니라 "작게만 쓰게" 만든다.
3. 도형마다 드는 길이가 다르다 → **룬 해금이 저절로 생긴다.**

| 도형 | 둘레 / 바운딩박스 한 변 |
|---|---|
| 꺾쇠(화살) | 1.8 |
| 삼각형(쉴드) | 3.0 |
| 원(힐) | 3.14 |
| 지그재그(연쇄) | 3.4 |
| 나선(소용돌이) | 4.4 |
| 별(별똥별) | 5.0 |

단계는 **총 별 개수**로 오른다 (0/4/9/15/22/30별 → 화면 높이의 0.55~1.60배).
별도 재화나 상점이 필요 없고, 별을 모을 이유가 바로 생긴다.

실제로 그릴 수 있는 크기(월드 유닛, 카메라 높이 8.4 기준):

| 단계 | 필요 별 | 원(힐) | 별(별똥별) | 힐 반경 | 별똥별 반경 |
|---|---|---|---|---|---|
| 1 | 0 | 1.47 | 0.92 | 0.74 | 0.51 |
| 3 | 9 | 2.41 | 1.51 | 1.20 | 0.83 |
| 6 | 30 | 4.28 | 2.69 | 2.14 | 1.48 |

1단계에서 별은 캐릭터 키(약 1.1)보다 작게밖에 못 그려서 별똥별이 사실상 안 쓰인다.
6단계면 힐 하나가 아군 셋을 덮는다.

**잉크가 떨어져 잘린 획은 발동하지 않는다.** 이게 없으면 제한이 무의미해진다 —
4분의 3만 그려진 원도 원으로 인식되는데 바운딩박스는 큰 원 그대로라,
**일부러 크게 그리다 잘리는 쪽이 이득**이 된다. 잘린 획은 마나도 쓰지 않으므로
잃는 건 슬로우로 흘려보낸 시간뿐이고, 그게 "더 작게 그려라"를 가르치는 비용이다.

효과 반경의 하한값도 같이 낮췄다(힐 0.5→0.4 등). 하한이 높으면 초반에 뭘 그리든
최소 반경이 나와서 잉크 성장이 화면에 안 보인다.

### 대장장이 — 룬 벼리기 · 문양 소환 (2026-08-01)

> 화면 이름은 "대장장이"(임시). 코드에서는 아직 `Workshop`/`WorkshopUI`로 되어 있다 —
> 이름이 확정되면 그때 한 번에 바꾼다. 임시 이름으로 코드를 고치면 두 번 바꾸게 된다.

**재화는 파편 하나뿐이다.** 강화와 뽑기가 같은 재화를 쓰므로
"이번엔 강화할까 뽑을까"라는 선택이 생긴다. 재화를 나누면 그 선택이 사라진다.

**뽑기 대상은 룬 도형이 아니라 문양이다.** 도형은 이 게임의 조작 그 자체라
운에 걸면 플레이어가 쓸 수 있는 손이 뽑기로 정해진다. 문양은 붙였다 뗄 수 있어
실패한 뽑기가 플레이를 막지 않는다.

| 시스템 | 올리는 것 | 이유 |
|---|---|---|
| 룬 강화 (Lv.1~10) | **위력만** (+8%/Lv) | 범위까지 올리면 잉크 제한이 무의미해지고, 마나까지 내리면 강화가 다른 축을 전부 덮는다 |
| 문양 (뽑기) | 위력 / 범위 / 마나 / 잉크 / 판정 | 축을 나눠야 뽑기 결과가 "숫자만 다른 같은 것"이 되지 않는다 |

- 문양 등급: 일반 52 / 희귀 30 / 영웅 14 / **전설 4%**
  (처음 2%로 잡았다가 올렸다 — 스테이지가 12개뿐이라 2%면 전설 기대치가 스윕 2회분이고,
  그러면 시스템이 있는 줄도 모르고 끝난다. 콘텐츠가 늘면 다시 조일 것)
- 장착 칸 2~5개, 별 12개마다 +1
- 같은 효과는 **더한다**(곱하지 않는다). 곱셈이면 모을수록 기하급수적으로 세져 후반이 무너진다
- 마나·잉크 할인은 60%에서 자른다. 공짜에 가까워지면 자원 설계가 사라진다
- **잉크 문양은 항상 전체 적용.** 잉크 한도는 그리기 시작할 때 정해지는데
  그 시점엔 무슨 룬을 그릴지 알 수 없어서 룬별 할인은 구현이 불가능하다

**경제 (실측 계산):**

| | |
|---|---|
| 전 스테이지 3별 첫 클리어 수급 | 2448 파편 |
| 룬 하나 만렙(Lv.10) | 1020 |
| 뽑기 1회 | 100 |
| 10연 소환 | 1000 (**할인 없음**, 영웅 이상 1개 확정) |
| 전설 1개 기대 | 2500 (≈ 스윕 1회) |

**한 번 훑으면 룬 두 개를 올리거나 뽑기 24회를 할 수 있다 — 둘 다는 못 한다.**
그게 이 시스템의 전부다. 다 되면 선택이 사라진다.

첫 클리어에 ×3, 재도전에 ×0.5를 준다. 쉬운 스테이지를 무한히 도는 게
최적해가 되면 안 되므로 앞으로 나아가는 쪽이 항상 이득이어야 한다.

**소환 연출 (`UI/GachaReveal.cs`)**

뽑기의 재미는 결과가 아니라 **결과가 나오기 직전의 몇 초**에 있다.
결과를 즉시 글자로 띄우면 확률 표를 확인하는 작업이 되고 두 번째부터 감흥이 없다.
그래서 세 박자로 나눴다: 모으고(Charge) → 터뜨리고(Flash) → 보여준다(Card).

| 설계 | 왜 |
|---|---|
| 등급이 **터지기 직전(65%)에** 색으로 새어 나온다 | 처음부터 등급색이면 기대가 사라지고, 끝까지 숨기면 쌓인 게 없다 |
| 높은 등급일수록 모으는 시간이 길다 (0.85초 → 2.0초) | **기다림 자체가 신호**가 된다 |
| 새 문양은 목록에 즉시 안 보인다 | 목록에 줄이 먼저 생기면 연출이 끝나기 전에 결과를 알아버린다 |
| 칸이 비었으면 자동 장착 | 뽑고 나서 목록을 뒤져 장착까지 해야 하면 소환이 사무 처리로 끝난다 |
| 연출 중 뒤쪽 UI는 `GUI.enabled = false` | 소환 중 다른 버튼이 눌리면 결과가 뜨기 전에 화면이 바뀐다 |

**10연 소환**

가격을 **할인하지 않았다.** 개당 가격을 깎으면 실측으로 맞춘 파편 경제(문양 하나 = 100)가
통째로 틀어진다. **확정 자체가 값어치**여야 한다.

확정을 "영웅 이상"으로 잡은 근거 — 희귀 확정은 의미가 없다(10번 뽑으면 어차피 99.9% 나온다).
영웅 이상은 그냥 뽑으면 **13.7%** 확률로 하나도 안 나오므로, 그 13.7%에서만 작동하는
보증이 된다. 있으나 마나도 아니고 압도적이지도 않다.

| 설계 | 왜 |
|---|---|
| 확정분은 **마지막 칸**에 넣는다 | 중간에 박히면 그 뒤 카드는 결과를 아는 상태로 넘어간다. 끝까지 볼 이유를 남긴다 |
| 모으는 시간은 **묶음 안 최고 등급**으로 정한다 | 평균으로 잡으면 전설이 섞여도 밋밋해진다 |
| 카드는 0.13초 간격으로 한 장씩 뒤집힌다 | 한 번에 다 뜨면 열 장이 그냥 표가 된다 |
| 자동 장착은 **등급 높은 것부터** | 순서대로 끼우면 일반이 자리를 차지하고 전설이 밖에 남는다 |
| 저장을 `BeginBatch/EndBatch`로 묶는다 | 문양 10개 + 자동장착까지 파일 쓰기가 15번 — 모바일에서 끊긴다 |

### Phase 8 — 최적화 · 피드백 (2026-08-01)

**최적화**
- [x] 인식 단일 패스 + 시작점 4개 → 획당 8.80ms → **2.20ms** (위 표)
- [x] 매칭용 `bool[n]`을 재사용 — 한 획에 수백 번 할당하던 것을 0으로
- [x] `OnGUI`의 `new GUIStyle(...)`을 전부 캐시. IMGUI에서 매 프레임 GUIStyle을 만들면
      화면에 아무 일이 없어도 GC가 계속 돈다
- [x] `TimeControl` — `Time.timeScale`을 쓰는 유일한 곳으로 통합.
      예전엔 TraceCapture가 값을 저장했다 되돌렸는데, 거기에 히트스톱을 얹으면
      서로의 값을 "원래 값"으로 착각해 덮어쓴다. **슬로우가 영영 안 풀리던 버그가
      정확히 그 구조였다.** 이제 요청자는 자기 요구값만 말하고 최종값은 한 곳에서 정한다

**피드백**
- [x] `FloatingText` — 피해·회복·보호막 숫자. **룬 피해는 크고 금색, 평타는 작게.**
      같은 크기로 띄우면 화면이 숫자로 덮여서 "내 룬이 얼마나 들어갔나"가 묻힌다
- [x] 힐이 만피에 들어가면 실제 회복된 양(0)을 띄운다 — 안 그러면 잘 쓴 줄 안다
- [x] 보호막이 막으면 "막음" 표시. 체력이 안 깎이는 건 화면상 '아무 일도 없음'과 같다
- [x] 히트스톱 — 별똥별 착탄과 PERFECT 시전에 아주 짧은 정지.
      같은 데미지도 훨씬 무겁게 느껴진다
- [x] 웨이브 배너 (`WAVE n/m`, `WAVE CLEAR`) — 적이 화면 밖에서 걸어 들어오는 구조라
      알려주지 않으면 웨이브가 넘어간 건지 아직 남은 건지 알 수 없다
- [x] 등급을 시전 위치에도 띄운다. 화면 중앙 표시는 궤적을 보던 시선에서 멀다

### Phase 9 — 게임 구색 (2026-08-01)

- [x] **현지화 (한국어 / English)** — `Meta/Loc.cs`. 첫 실행 시 시스템 언어를 따르고,
      한국어가 아니면 영어로 (지원 안 하는 언어를 한국어로 띄우는 것보다 낫다)
- [x] **설정 화면** — 언어 · 배경음 · 효과음 · 시전 슬로우 · 전체화면 · 진단 패널 · 진행 초기화
- [x] **일시정지** (Esc) — 계속 / 설정 / 처음부터 / 포기
- [x] 설정은 `settings.json`에 즉시 저장

**설정을 바꾸면 즉시 저장·적용한다.** "적용" 버튼을 두면 안 누르고 나가는 사람이
반드시 생기고, 그러면 설정을 바꿨는데 안 바뀌었다고 느낀다.

**시전 슬로우를 설정에 노출한 게 중요하다.** 이건 화면 옵션이 아니라 **난이도 손잡이**다 —
손이 느린 사람은 값을 낮춰서 그릴 시간을 벌 수 있다. 제스처가 핵심인 게임에서
"손이 느리면 못 한다"는 벽을 옵션 하나로 없앨 수 있으면 그렇게 해야 한다.

**진행 초기화는 두 번 눌러야 실행된다.** 되돌릴 수 없는 버튼을 한 번에 두면
반드시 누가 실수로 누른다.

**일시정지는 상태가 아니라 전투 위의 플래그다.** 상태로 만들면
"일시정지 → 설정 → 돌아오기" 같은 전이가 상태 표를 두 배로 만든다.
전투는 계속 `Battle`이고 시간만 멈춘 것이 실제 구조에 더 가깝다.

문자열 키는 `Loc` 표 한 곳에 모여 있고, **키를 못 찾으면 예외 대신 키 자체를 반환한다** —
번역이 빠졌을 때 게임이 멈추는 것보다 화면에 `stage.13`이 보이는 편이 낫다.
